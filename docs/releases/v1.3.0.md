# Fluval BLE v1.3.0

v1.3.0 makes the integration's repairs honest: one that no longer outlives the
problem it describes, one that finally appears when the fixture is genuinely
gone, and a **Fix** button that walks the same recovery ladder an operator
would walk by hand.

## Added

- **Repair `<mac>_unreachable`**, raised once Home Assistant has been unable to
  hold a BLE link to the fixture for 15 minutes, and deleted the moment the
  link returns.
- **Both repairs are fixable.** The Fix button opens a wizard that escalates,
  cheapest rung first: check again -> reload the integration -> restart the
  ESPHome proxy that was carrying the link -> cut and restore mains power
  through a switch you pick (remembered in the entry's options for next time).
  A schedule problem starts one rung earlier by re-pushing the expected mode
  and schedule through the guardian.
  The proxy rung appears only when a proxy is known *and* exposes the matching
  `esphome` action, and it reports itself honestly: proxy firmware refuses a
  restart within 20 minutes of booting, so the wizard says the proxy was asked
  rather than claiming it rebooted.
- **The carrying proxy is recorded** in the entry's options
  (`last_holding_proxy`) while the link is up, because an unreachable fixture
  is held by nobody and there is nothing left to discover at Fix time. Written
  only when it changes, and never triggers a reload. Stored as the bare
  ESPHome node name, not habluetooth's `"<node> (<MAC>)"` display name, which
  slugifies to an action that does not exist.

## Fixed

- **A repair could outlive its condition.** Live: `44A6E570F18D_schedule_problem`
  was raised at 12:22, the entry reloaded at 12:38, the guardian cleared the
  condition at 13:00 - and the repair was still open 13 hours later. Deletion
  was gated on an in-memory "previously synced" flag that the reload reset, so
  the next notification recorded the new state without syncing. Repairs are now
  reconciled against what the repairs registry actually holds, on every
  guardian notification and once when the entity is added, so a reload always
  converges. Reconciliation also replaces a stored repair whose severity or
  fixability no longer matches the code, so an upgrade does not leave an
  operator staring at a Fix-less repair until it clears once.
- **The unreachable repair could never be raised on a household that heals by
  reloading.** Measured on 2026-09-09 during a deliberate 21-minute power cut:
  link drop 22:24:37, `automation.ble_proxy_autoheal` reloaded the entry at
  22:35:00 and 22:40:00, and every reload built a fresh watcher whose
  15-minute countdown restarted at zero - so no repair ever appeared. Home
  Assistant's own last-advertisement hint was empty, because the fixture had
  not been heard at all since the restart. The moment a link first went down is
  now held per BLE address in process-scoped state that survives reloads and is
  never overwritten; a rebuilt watcher arms for the remainder of the window, or
  raises immediately when the window has already passed.
- **The ladder refused to run when it was needed most.** A fixture that is dark
  at startup leaves its entry retrying setup rather than loaded, and the wizard
  aborted in that state - withholding the only rungs that can help a radio
  nothing can hear. Reload, proxy restart and power cycle now all work on a
  retrying entry; with no device to ask, recovery is judged by the same
  connectable advertisement setup itself waits for.
