# Fluval BLE v1.2.0

v1.2.0 makes the BLE link something the integration holds and heals, and makes
a user's command outrank the guardian's supervision work.

## Changed

- **The GATT link is held by default.** `active_time` now defaults to `0`
  (persistent) instead of `120` s. A held link answers a command in
  ~0.4-2 s where a fresh ESPHome-proxy connect costs 2-6 s; the option and
  its validation (0, or 30-600) are unchanged, so setting a finite idle
  window restores the previous behaviour exactly.
- **User commands preempt the guardian.** Everything reachable from an
  entity or service call (light on/off/brightness/effect/channels, mode
  select, buttons, schedule services) takes the device's command lock ahead
  of guardian work, and the guardian now stands aside - reporting a new
  `deferred` status and retrying 20 s later - rather than making a button
  press wait out a multi-step check. A user command's overall deadline drops
  from 60 s to 15 s; only native schedule writes keep the 90 s ceiling their
  settle-and-verify sequence needs.

## Added

- **`sensor.<device>_connection`** (diagnostic, enabled by default) reports
  the name of the ESPHome proxy or adapter currently carrying the fixture's
  GATT link - or `disconnected` - so a heal automation can restart the one
  proxy that matters instead of one other devices are holding. Attributes:
  `hold`, `drops_1h`, `last_drop`, `reconnect_attempt`. The proxy name is
  pushed live from habluetooth's slot allocations, so a reconnect that roams
  to a different proxy is visible immediately.

## Fixed

- A queued button press could consume its whole 60 s deadline waiting behind
  a wedged guardian clock sync and return an error while the radio itself was
  answering in ~200 ms (observed live 2026-09-07 21:40).
- `sensor.<device>_last_seen` froze the moment a held link came up: it was fed
  only by advertisements, which a connected fixture emits rarely. Every
  successful GATT exchange (heartbeat read, state read, command write, inbound
  notification) now counts as "seen", so nothing derived from `last_seen`
  (including the reachability window) goes stale on a healthy held link.
- Reconnects after an unexpected drop follow a bounded backoff (1, 2, 5, 10,
  30, 60 s, capped, +-20 % jitter) instead of retrying every second, log the
  proxy that took the link at INFO, and warn once per 10 consecutive failures.
  Because every reconnect goes through `bleak_retry_connector`, Home
  Assistant re-scores all proxies each time and the link roams to the best one
  on its own.
